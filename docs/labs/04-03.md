# Lab 04-03 — Gemma 실시간 서빙

> **사전 학습 교안 / 미실행**. 학습 도중 사용한 실제 버전·명령어·관측값은 별도의 학습 기록에 남깁니다.

## 학습 목표와 상황

노드 복구가 빨라도 모델 재다운로드와 VRAM 로딩에 시간이 걸리면 사용자 서비스의 복구시간은 길어진다. GPU 상시 점유는 배치 풀의 용량도 줄인다.

## 핵심 개념

1. 채팅 서비스는 모델 가중치를 GPU VRAM에 적재한 프로세스를 유지하여 요청마다 초기 로딩을 반복하지 않는다. 이를 위해 GPU를 상시 요청할 수 있으며 유휴 상태에도 다른 Job이 그 GPU를 사용하지 못할 수 있다.

2. 실시간 서버는 Deployment/Service 방식이 자연스럽고, 종료 가능한 배치 추론은 Job 방식이 자연스럽다. 이 둘의 스케줄링과 복구 정책은 분리해야 한다.

3. Readiness Probe는 서비스가 새 요청을 받을 준비가 됐는지, Liveness Probe는 재시작이 필요한 상태인지 확인한다. 모델 로딩 시간이 길면 Startup Probe도 검토한다.

## 내부 동작 경로

Deployment GPU Pod 시작 → 모델 VRAM 로딩 → Readiness 승인 → Service 엔드포인트 등록 → FastAPI가 추론 호출 → 토큰 응답 반환.

## 실습 준비

Phase 01에서 검증한 모델·양자화·런타임 사용, 모델/포트와 요청 제한·프로브 시간 정의.

## 직접 수행할 실습

1. 단일 인스턴스에서 서빙 엔드포인트 준비 상태 확인 후 질문 응답.
2. 같은 모델의 종료형 배치 추론 Job과 Deployment를 각각 실행하여 VRAM 점유 지속성 비교.
3. 동시 요청과 긴 프롬프트를 소규모로 보내 응답 지연·실패 상태 조사.

## 검증·완료 기준

- 모델 콜드 스타트와 워밍된 요청의 지연 분리
- 프로브와 서비스 종료 시 GPU 반환 확인

## 서술형 질문

1. 챗봇 프로세스가 대기 중이어도 다른 팀 GPU Job이 못 뜰 수 있는 이유는?
2. 노드 교체 완료 시간과 사용자가 다시 채팅할 수 있는 시간은 왜 다른가?
