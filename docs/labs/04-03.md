# Lab 04-03 — NVIDIA Device Plugin·GPU Job 검증

> **2026-11-13 개편 · GPU Linux 서버에서 EKS로 확장** · 환경: G2. **실제 EKS GPU 실습 미수행**. [Lab 이관](../migration-2026-11-13.md) 및 [운영 비용 게이트](../operations.md) 참조.

## 운영 요구사항

EKS에서는 물리 GPU가 OS에 보이는 사실과 스케줄러가 요청할 수 있는 `nvidia.com/gpu` 자원을 등록하는 과정이 다르다.

## 내부 동작

`GPU + Linux Driver/Runtime → NVIDIA Device Plugin → kubelet Capacity/Allocatable → kube-scheduler → GPU Pod → CUDA/YOLO`

## 학습·실습 순서

1. G1에서 성공한 GPU 컨테이너/YOLO 이미지와 데이터 입력·출력 계약을 그대로 사용하여 G2 적용 계획 수립.
2. Node별 NVIDIA Driver/Toolkit·Device Plugin 버전/설치 상태를 확인하고 `kubectl describe node`의 GPU Capacity/Allocatable와 Plugin 로그를 검증.
3. YOLO Job에서 `resources.limits.nvidia.com/gpu: 1` 형태의 정수 장치 요청을 설정하고 서로 다른 두 GPU Worker에 실제 학습 Job 배치.
4. Pod Events/스케줄링 원인, GPU가 실제 할당되었는지, PyTorch CUDA 연산·YOLO 결과를 각각 별개 증거로 기록.
5. GPU 노드 1대 미인식/자원 부족 시 남은 용량·Node 상태와 Pod Pending을 분리해 원인을 설명.

## 완료 증거

Node Capacity/Allocatable, Plugin/Kubelet 이벤트, Pod 배치, 실제 YOLO GPU Job 출력 및 비용.

실제 실행 전에는 결과·복구·사용률을 만들어내지 않는다. AWS GPU 8 vCPU 쿼터는 승인됐지만 AZ 용량과 실제 실행 비용·동작은 별도 검증이 필요하다.

## 서술형 인출 문제

GPU 장치가 `nvidia-smi`에 보이는데 `nvidia.com/gpu` Capacity가 비어 있다면 어디부터 진단할까?
