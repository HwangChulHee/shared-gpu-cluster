# Lab 05-03 — DCGM 기반 GPU 모니터링

> **사전 학습 교안 / 미실행**. 학습 도중 사용한 실제 버전·명령어·관측값은 별도의 학습 기록에 남깁니다.

## 학습 목표와 상황

Pod는 Running인데 GPU 메트릭이 사라지면 작업 실패보다 Exporter Pod/Prometheus Target 상태를 먼저 점검할 수 있다.

## 핵심 개념

1. NVML/DCGM은 GPU 장치 텔레메트리를 제공하고 DCGM exporter는 이를 Prometheus 메트릭으로 노출한다. Prometheus는 수집·저장을, Grafana는 조회·시각화를 담당한다.

2. GPU 사용률, VRAM 사용량, 전력/온도와 Kubernetes Job 상태는 출처가 다르다. GPU가 100% 예약되었어도 실제 연산 사용률은 낮을 수 있다.

3. Exporter가 동작하지 않아 메트릭이 비어 있는 경우를 GPU 유휴 또는 장애라고 오판하면 안 된다. scrape 대상과 레이블·카디널리티를 확인한다.

## 내부 동작 경로

GPU/NVML/DCGM → DCGM exporter /metrics → Prometheus scrape → Grafana 질의; K8s Events/kube-state-metrics → 작업 상태 대조.

## 실습 준비

GPU 노드에 DCGM exporter 배치, CPU 노드에 적절한 모니터링 스택. 저장 용량·리소스 비용 추정.

## 직접 수행할 실습

1. 실제 GPU Worker에서 DCGM exporter 메트릭 엔드포인트 점검.
2. Prometheus Targets와 GPU별 Grafana Panel 구성.
3. Gemma/YOLO/XGBoost를 순서대로 실행하며 GPU 사용률·VRAM·Pod 상태를 같은 타임라인에 표시.

## 검증·완료 기준

- 실제 메트릭 샘플 및 대시보드 캡처
- GPU 메트릭 수집 실패와 GPU 연산 부하 0을 구분

## 서술형 질문

1. GPU가 Allocated인데 Utilization 0%일 수 있는 이유는?
2. Grafana에 데이터가 보이지 않을 때 어떤 계층부터 점검하겠는가?

## 실습 확장: 수집 경로 확인

**확인 순서:** (1) GPU 노드의 실제 `nvidia-smi` 상태 → (2) GPU 노드에 exporter Pod 실행 → (3) exporter의 `/metrics` HTTP 응답 → (4) Prometheus scrape target의 `UP` → (5) Grafana 패널 값.

```bash
kubectl get pods -A -o wide
kubectl get services -A
kubectl get pods -n <MONITORING-NS> -o wide
```

`<MONITORING-NS>`는 실제 설치 Namespace로 치환한다. exporter/Prometheus Helm 차트, 포트, 서비스 이름은 사용한 **버전·릴리스 이름**을 먼저 확인한다. GPU가 없는 CPU 시스템 노드와 GPU 노드의 exporter 배치도 구별한다.

Prometheus 쿼리는 exporter 버전별 실제 노출 이름을 `/metrics`에서 확인한다. 예를 들어 `DCGM_FI_DEV_GPU_UTIL`, `DCGM_FI_DEV_FB_USED`가 보이면 각 지표의 단위를 확인하고 그래프에 반영한다. **메트릭이 없으면 0으로 치환해 GPU 유휴라고 해석하지 않는다.**

시연 증거: 동일 타임라인에 GPU 사용률/메모리, Kubernetes Pod/Job 상태, 사용자 작업 ID의 실행시간 표시. exporter의 GPU 메트릭만으로 작업별 점유시간이나 사용자 요청 지연이 자동 측정되는 것은 아니다.
