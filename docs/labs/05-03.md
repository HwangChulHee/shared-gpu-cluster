# Lab 05-03 — GPU 클러스터 관측과 운영 진단

> **2026-11-13 개편 · GPU Linux 서버에서 EKS로 확장** · 환경: G2. **실제 EKS GPU 실습 미수행**. [Lab 이관](../migration-2026-11-13.md) 및 [운영 비용 게이트](../operations.md) 참조.

## GPU 비용 최적화 실행 구간

> 공통 기준: [GPU 실행 게이트·G1/G2 런북](../gpu-execution-gates.md). **OFF 준비를 GPU 실측 완료로 간주하지 않는다.**

| 구간 | 수행할 작업·완료 기준 |
|---|---|
| **GPU OFF-1 · 사전 학습/로컬 검증** | G1 Prometheus·Grafana 재사용, kube-state-metrics·Pod/Node/Job 패널·수집 규칙과 Events 진단을 로컬 구성 |
| **GPU ON · 최소 시간 실측** | G2 DCGM/노드/클러스터 메트릭 연결, Job 3개 타임라인·GPU 지표 수집 |
| **GPU OFF-2 · 분석/기록** | GPU/Pod/Job 지표 연결·경보와 관측 한계 문서화 |

GPU가 필요한 실측은 사전에 준비한 명령·성공 기준·보존 경로에 따라 실행한다. 실패하면 진단 시간·비용 상한을 적용하고 후속 실험을 멈춘다.

## 운영 요구사항

G1에서 만든 GPU·Linux 메트릭을 Node/Pod/Job에 연결해야 EKS에서 어떤 작업이 왜 기다리거나 종료됐는지 분석할 수 있다.

## 내부 동작

`G1 DCGM/node exporter → Prometheus/Grafana + K8s kube-state-metrics/Events → GPU Node/Pod/Job 상관관계`

## 학습·실습 순서

1. G1 대시보드의 GPU Util/VRAM·CPU/RAM/디스크 메트릭을 재사용하고, G2의 GPU Worker별 식별자/리소스 레이블 대응 방식을 설계.
2. kube-state-metrics 등으로 Node Ready, Pod phase, Job 상태를 수집하며 Kubernetes Events/describe는 별도 이벤트 진단 경로로 확인.
3. GPU 2대에 Job 3개를 제출한 05-01 시나리오에서 실행/대기·자원 반환과 GPU 실제 사용 메트릭을 같은 시간축에 표시.
4. Pod Pending이 GPU 사용률과 무관하게 스케줄러·taint·요청량 때문에 발생할 수 있음을 로그와 메트릭으로 구분.
5. 정상 경보 후보와 실측 결과, 메트릭 한계, 클러스터 운영 복잡도를 정리. Kueue 없이 필수 완료 가능.

## 완료 증거

실제 PromQL/대시보드, 작업별 GPU·Node·Pod/Job 이벤트 타임라인, 진단 절차.

실제 실행 전에는 결과·복구·사용률을 만들어내지 않는다. AWS GPU 8 vCPU 쿼터는 승인됐지만 AZ 용량과 실제 실행 비용·동작은 별도 검증이 필요하다.

## 서술형 인출 문제

GPU Util이 낮은데 Pod Pending이 지속된다면 어떤 스케줄러·Node·Pod 증거를 우선 볼까?

## 선택 심화 — Kueue

실측 결과 여러 팀 간 할당량 보장·큐 관리가 필요하다는 요구가 생길 때만 Kueue LocalQueue/ClusterQueue·Admission을 별도 실험으로 검토한다. **Borrowing·Preemption 정책 설계와 사용자 서비스 개발은 필수 범위가 아니다.** [Runway 사례](https://runway.com/news/engineering/no-idle-gpus-managing-research-compute-at-runway)는 논리적 Admission과 실제 Pod Scheduling 차이를 이해하는 참고자료다. Kueue를 설치하지 않아도 이 Lab은 완료할 수 있다.
