# Lab 06-01 — GPU OOM·메모리 분석

> **새 7 Phase / 21 Lab 교안, 미실측** · 환경: G1. 동일 번호를 사용한 이전 교안과 학습 기록은 [이관표](../migration-2026-11-12.md) 참조.

## 학습 목표·왜 필요한가

Batch 증가에 따른 Activation 저장과 VRAM 추세를 측정하고 CUDA OOM과 Linux OOM을 구분한다.

## 내부 동작·구성 요소

YOLO Batch 변경→GPU VRAM peak→CUDA OOM/정상→로그 분석→복구.

## 실무 시나리오

Batch를 단계적으로 변경해 정상 기준선과 CUDA 오류를 비교한다.

## 준비·실습 (실제 사용자가 실행)

1. **사전 분석:** 위 시나리오의 운영 요구사항과 예상 실패 계층을 서술한다.
2. **비용 게이트:** 환경 G1. G1/G2가 포함될 경우 먼저 AWS GPU 쿼터 승인, EC2/EKS/네트워크/스토리지 비용, 생성·삭제 경로를 확인한다. 승인 전에는 GPU 실행을 진행하지 않는다.
3. **실행 준비:** AMI/Driver/CUDA/컨테이너, YOLO·데이터셋, Batch/Epoch, seed, 캐시 상태를 고정한다. 실행 명령은 실제 버전과 환경을 확인한 뒤 단계별로 확정한다.
4. **실행:** Batch를 단계적으로 변경해 정상 기준선과 CUDA 오류를 비교한다.
5. **관측·분석:** 정상 기준선을 먼저 기록한 뒤 GPU·CPU·RAM·스토리지·Pod/Job Events 중 관련 지표를 수집한다. 대조군, 예상/실측, 반증 조건, 통제된 실패 주입 여부를 구분한다.
6. **정리:** 결과/Checkpoint 보존, Terraform/EC2/EKS/NAT/EBS/S3 잔여 과금 자원 점검.

## 완료 증거

Batch-메모리 추세, 오류 원문, CPU RAM 확인, 정상 복구.

실측이 없다면 계획 단계로 남긴다. [실제 사례·공식 근거](https://docs.pytorch.org/docs/stable/notes/cuda.html#memory-management)는 출처 유형을 분리해서 기록하며, 장애 주입을 자연 발생 장애처럼 표현하지 않는다.

## 서술형 점검 (하나씩 진행)

CPU RAM이 부족한 OS OOM과 CUDA OOM은 어떻게 다른가?
