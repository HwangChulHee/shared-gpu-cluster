# Lab 06-03 — GPU 인식 계층 장애

> **학습 교안 / 실행 전**. 아래 예시는 실제 테스트 결과가 아닙니다.

## 이 Lab을 배우는 이유

호스트 `nvidia-smi`가 정상이고 GPU Allocatable 0이라면, 물리 GPU 고장으로 추정하기보다 Device Plugin 로그·설정과 kubelet 등록 상태를 먼저 확인한다.

## 핵심 개념과 내부 원리

1. GPU가 호스트 OS에서 보이지 않는 문제와 kubelet에 확장 자원으로 등록되지 않는 문제는 다른 계층이다. 물리 장치→Driver→NVML→Device Plugin→kubelet→Scheduler→컨테이너 런타임 순서로 분리한다.

2. Device Plugin 장애나 불일치 구성은 `nvidia.com/gpu` Allocatable 감소·Plugin 로그 오류·GPU Pod 스케줄링 실패로 나타날 수 있다. 하지만 모든 구성 오류가 즉시 같은 증상을 만들지는 않는다.

3. 기존 실행 Pod와 신규 GPU Pod에 나타나는 영향은 서로 다를 수 있다. 정상 GPU 사용 중인 프로세스를 강제로 손상시키는 실험 대신 지원되는 안전한 Plugin 구성 변경으로 재현한다.

## 시스템 동작 흐름

Pod Pending/실행 실패 관찰 → Node Capacity/Allocatable 확인 → Device Plugin DaemonSet 로그 → Host `nvidia-smi` → Container Toolkit 점검 → 설정 복구 → 새 GPU Job 정상 검증.

## 실습 전 준비

정상 시점의 Node Capacity/Allocatable·Device Plugin 버전·호스트 GPU 정보 백업. 복구 매니페스트와 노드 종료 방법 확보.

## 직접 실습

1. 정상 상황의 Host GPU·Node GPU·Pod 실행 정보를 수집.
2. 허용된 실습 환경에서 Device Plugin 배포/설정의 통제된 오류를 주입하여 새 GPU Job 증상 관찰.
3. 정상 설정 복구 후 Node Allocatable·GPU 컨테이너 실행까지 검증.

## 검증 기준과 남길 증거

- 계층별 증거가 동일한 고장 원인을 가리키는지 조사
- 실제 물리 GPU 손상이나 강제 드라이버 손상을 유도하지 않음

## 서술형 인출 질문

1. Node Ready지만 `nvidia.com/gpu`가 0일 때 가장 먼저 확인할 단서는?
2. 호스트에서 GPU가 보이는 것과 GPU Pod에서 CUDA 연산이 가능한 것은 왜 다른가?
