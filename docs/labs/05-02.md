# Lab 05-02 — GPU 서비스 네트워킹

> **사전 학습 교안 / 미실행**. 학습 도중 사용한 실제 버전·명령어·관측값은 별도의 학습 기록에 남깁니다.

## 학습 목표와 상황

Gemma에 접속되지 않는데 GPU 노드가 Ready라는 사실만으로 네트워크가 정상이란 결론을 낼 수 없다. DNS, Service Endpoint, SG, Policy, Pod 포트를 차례로 확인한다.

## 핵심 개념

1. VPC CNI는 EKS의 Pod IP 연결을 책임진다. Service/DNS는 변하는 Pod 주소를 추상화하며, Kubernetes API 서버 호출과 Gemma 추론 요청은 다른 트래픽 경로다.

2. Security Group은 ENI/인스턴스 수준의 통신 정책이고 NetworkPolicy는 Pod 워크로드 통신 제한을 다룬다. NetworkPolicy는 플러그인의 지원·활성화 상태를 확인해야 실제 적용된다.

3. 데이터 전송이 느리면 모델 로딩과 서비스 지연이 증가한다. GPU Worker 간 대역폭/MTU와 외부 저장소까지의 경로를 구분해 측정한다.

## 내부 동작 경로

사용자→FastAPI Service→Gemma Service→GPU Pod의 HTTP 경로; FastAPI→K8s API의 제어 경로; Pod→S3/EFS의 데이터 경로.

## 실습 준비

VPC·Pod CIDR·Namespace·Service 이름, EKS CNI의 NetworkPolicy 지원 구성 확인.

## 직접 수행할 실습

1. FastAPI Pod에서 Gemma Service로 DNS/HTTP 연결성 점검.
2. GPU Job이 S3/EFS에 접근하는 경로 및 지연 확인.
3. 실험 지원 시 NetworkPolicy로 불필요한 통신을 차단하고 허용된 흐름만 통과하는지 확인.

## 검증·완료 기준

- 3개 트래픽 경로별 관측값과 실패 가능 지점 기록
- SG 제한·NetworkPolicy 거절·Service/Endpoint 오류를 구별

## 서술형 질문

1. API Server가 살아 있는데 Gemma HTTP 요청은 실패할 수 있는 이유는?
2. Security Group과 NetworkPolicy는 어떤 차원에서 적용되는가?
