# Lab 04-02 — FastAPI 작업 실행 API

> **사전 학습 교안 / 미실행**. 학습 도중 사용한 실제 버전·명령어·관측값은 별도의 학습 기록에 남깁니다.

## 학습 목표와 상황

사용자가 학습 버튼을 두 번 눌러 같은 모델 학습이 두 개 실행되면 공유 GPU를 불필요하게 점유한다. 요청 식별과 중복 처리 방침이 필요하다.

## 핵심 개념

1. FastAPI는 직접 GPU를 제어하는 대신 제한된 Kubernetes API 작업을 요청한다. Kubernetes Job 생성은 제어 경로이며 작업 결과 업로드·조회는 데이터 경로다.

2. Kubernetes Job 상태만으로 모델의 실제 성능 지표와 결과 파일을 알 수 없다. Job 완료 후 S3 객체·메타데이터를 확인하는 프로토콜이 필요하다.

3. API 재시도 시 동일 요청의 Job이 무한 증식하지 않도록 idempotency/요청 ID와 Job 이름 정책을 정의한다.

## 내부 동작 경로

요청 파라미터 검증 → 허용된 Job 템플릿 생성 → K8s API Job 생성 → 작업이 S3에 결과 저장 → API가 Job 상태와 S3 결과 조회.

## 실습 준비

테스트 Namespace, S3 결과 경로, Job Template, FastAPI ServiceAccount/RBAC 계획.

## 직접 수행할 실습

1. YOLO/XGBoost만 선택 가능한 고정된 API 스키마 작성. 임의 이미지는 금지.
2. Job 생성·목록·상태·로그·결과 API 최소 구현.
3. 로컬 가짜 클라이언트와 실제 EKS에서 기능 검증. API를 재호출해 중복 생성 여부 확인.

## 검증·완료 기준

- K8s API로 생성된 Job 이름과 S3 결과의 요청 ID 일치
- 백엔드가 과도한 Kubernetes 권한을 갖지 않음

## 서술형 질문

1. Job 생성과 사용자 결과 조회는 왜 다른 경로인가?
2. HTTP 재시도가 중복 GPU Job을 만들지 않으려면 어떤 방어가 필요한가?

## 실습 확장: API 계약과 실행 경계

최소 API 형태(설계 예시, 아직 구현·배포 전):

```text
POST /jobs               → 202 Accepted {job_id, status}
GET  /jobs/{job_id}       → {status, model, team, timestamps}
GET  /jobs/{job_id}/logs  → 제한된 실행 로그
GET  /jobs/{job_id}/result→ 완료 후 S3 결과를 조회/제공
```

**처리 흐름:** (1) 서버에서 모델 종류·데이터셋·Epoch 범위·팀 권한 검증 → (2) 요청 ID 생성·중복 확인 → (3) 허용된 템플릿만으로 해당 Namespace에 Job 생성 → (4) Job 상태 조회 → (5) S3 결과 확인. `202`는 **작업 접수**일 뿐 학습 성공을 뜻하지 않는다.

**실습 검증 시나리오:** 같은 요청 ID를 두 번 제출해 GPU Job이 중복 생성되지 않는지 확인한다. 다른 팀의 Job ID로 상태와 S3 결과를 요청해 거절되는지 확인한다. Kubernetes ServiceAccount에 `create/get/list/watch` 등 필요한 최소 API·Namespace 권한만 부여하고, 로그/secret/Pod exec 등의 권한을 무심코 전체 허용하지 않는다.

UI가 보내는 팀 이름은 인증 증명이 아니다. 데모 신뢰 경계와 서버 정책을 [접근 제어 Lab](04-04.md)에서 확정한다.
