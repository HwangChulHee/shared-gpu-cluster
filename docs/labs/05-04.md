# Lab 05-04 — 서비스 지표·정상 기준선

> **사전 학습 교안 / 미실행**. 학습 도중 사용한 실제 버전·명령어·관측값은 별도의 학습 기록에 남깁니다.

## 학습 목표와 상황

Gemma 첫 요청 40초와 다음 요청 1초를 단순 평균으로 합치면 초기 모델 로딩 문제와 토큰 생성 성능이 섞인다.

## 핵심 개념

1. DCGM의 장치 메트릭만으로 사용자 경험을 설명할 수 없다. Gemma 응답 지연, YOLO 학습시간, XGBoost 작업 대기시간은 애플리케이션/Job에서 계측해야 한다.

2. 평균만 기록하면 긴 지연을 숨길 수 있다. 서비스에는 p50/p95 지연과 요청 수, 배치 작업에는 제출→시작 대기시간과 시작→종료 실행시간을 구분한다.

3. 모델 캐시(Cold/Warm), seed, 데이터셋, 동시 요청 수, GPU 인스턴스가 다르면 같은 작업이라도 결과를 직접 비교하기 어렵다.

## 내부 동작 경로

API 제출/요청 Timestamp → Job/Pod 시작·종료 Timestamp → 서비스 결과와 지표 → DCGM·Node 지표와 시간 정렬 → 기준선 표 작성.

## 실습 준비

측정할 지표의 이름·단위·출처와 기본 입력·반복 횟수 고정.

## 직접 수행할 실습

1. Gemma 첫 요청/워밍 후 응답 및 동시성별 지연 수집.
2. YOLO/XGBoost 제출·실행·종료 시간과 GPU 메트릭 연결.
3. 동일 조건 최소 3회 반복 여부를 명시하고 결과의 변동과 한계를 기록.

## 검증·완료 기준

- 정상 기준선과 비교 가능한 실행 조건 기록
- GPU 사용률만으로 처리량/지연 개선을 주장하지 않음

## 서술형 질문

1. 평균 지연만 보고 사용자 서비스 품질을 판단하면 어떤 문제가 생기는가?
2. 대기시간과 실행시간을 나눠야 하는 이유는?
