# Lab 03-01 — GPU Job 스케줄링

> **학습 교안 / 미실행**. 실행 절차는 실제 AWS/패키지 버전에 맞춰 고정한 뒤 수행합니다. 예상 결과는 실측 결과가 아닙니다.

## 학습 맥락과 목표

GPU 노드 2대가 각각 한 장씩이라면 GPU 한 장 요청 Job 3개를 동시에 실행할 수 없다. 세 번째 Job은 자원을 기다리며, 언제 실행되는지는 기존 Job이 끝나는 시점·스케줄링 결과에 달렸다.

## 핵심 개념·원리

1. Kubernetes는 GPU 확장 자원을 대체로 정수 단위로 요청한다. Pod가 `nvidia.com/gpu: 1`을 요구하면 해당 수의 미할당 GPU가 있어야 배치 가능하다.

2. Scheduler는 노드 필터링과 점수화 등을 거쳐 노드를 선택한다. 노드가 자원 요구를 만족하지 못하면 Pod가 Pending으로 남고 Events에 이유가 드러난다.

3. Pod 완료·삭제 후 GPU 자원은 다른 작업이 사용할 수 있지만, Job Pod의 자원 해제와 새 작업의 실제 Running 시점은 별도로 관찰한다.

## 내부 흐름

Job 제출 → Job Controller가 Pod 생성 → Scheduler가 GPU 요청을 만족하는 Node 선택 → kubelet/runtime 실행 → Job 완료/Pod 종료 → GPU 자원 반환 → 대기 Pod 배치.

## 실습 준비

길이가 충분하고 종료 가능한 GPU Job 3개 준비. Gemma 채팅의 지속형 서버는 이 실험에서 제외.

## 실습

1. GPU 1개를 요구하는 두 작업을 각각 실행한 뒤 세 번째 작업을 제출.
2. 세 번째 Pod의 상태와 `kubectl describe pod` Events를 기록.
3. 기존 Job 하나를 정상 종료시켜 GPU 반환과 세 번째 Job의 배치를 관찰.

## 검증할 증거

- Pod/Node/GPU 요청값과 작업별 제출·실행시각 수집
- GPU 활용률과 GPU 할당 상태의 차이 설명

## 서술형 인출 질문

2. Job 하나가 완료되었다고 GPU가 항상 즉시 다른 Job에 할당되지는 않는 이유는?
