# Lab 07-03 — 최종 기술 보고와 한계

> **학습 교안 / 실행 전**. 아래 예시는 실제 테스트 결과가 아닙니다.

## 이 Lab을 배우는 이유

GPU 장애 실험이 완전 자동 복구에 실패해도, 왜 실패했는지 정량화하고 용량·체크포인트 정책을 개선했다면 운영 엔지니어링 성과가 된다.

## 핵심 개념과 내부 원리

1. 기술 포트폴리오는 구성 요소의 수보다 설계 의사결정, 검증 가능한 결과, 예상과 실제가 달랐던 지점에 더 가치가 있다.

2. 'GPU 고가용성 구현', '공정성 향상' 등의 주장은 구체적 테스트 조건과 수치, 실패 사례, 한계 설명 없이 사용하지 않는다.

3. CPU/GPU 스택, Kueue, 스토리지, 자동 복구의 대안과 비용을 비교하면서도 직접 검증하지 않은 Slurm·RDMA·InfiniBand는 향후 과제로 분리한다.

## 시스템 동작 흐름

문제 정의 → 요구사항 → 아키텍처와 대안 → 실습 기록/학습 성과 → 정상 기준선 → 비교/장애 결과 → 원인·개선 → 비용·한계 → 재현 방법.

## 실습 전 준비

Phase 01~07 기록, 실험별 표·그래프·로그, 비용·제약, 코드 커밋·버전 근거 취합.

## 직접 실습

1. README에 구현 완료·계획·미구현 기능을 구분.
2. T/F 시나리오 실측 값과 재현 조건, RCA/Runbook을 연결.
3. 기술 선택 이유, 대안, 비용·안정성 trade-off 및 후속 개선 사항을 한 문서로 요약.

## 검증 기준과 남길 증거

- 모든 핵심 주장이 검증 자료 또는 설계 근거를 가리킴
- 사용자/부서 정보와 민감한 AWS 계정·비밀 값이 공개되지 않음

## 서술형 인출 질문

1. 성능이 개선됐다는 주장에 필요한 최소한의 실험 증거는?
2. 클라우드 GPU 포트폴리오로 검증할 수 없는 물리 GPU 서버/HPC 영역은 무엇인가?
