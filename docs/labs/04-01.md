## GPU 비용 최적화 실행 구간

> 공통 기준: [GPU 실행 게이트·G1/G2 런북](../gpu-execution-gates.md). **OFF 준비가 완료되어도 GPU 실측을 완료한 것은 아니다.** 실제 출력과 가설/계획을 구분한다.

| 구간 | 수행할 작업·완료 기준 |
|---|---|
| **GPU OFF-1 · 사전 학습/로컬 검증** | G1 경험을 기반으로 EKS VPC·API/노드·ECR/S3·IAM·NAT/Endpoint 설계, Terraform fmt/validate/plan·비용/정리 계획 |
| **GPU ON · 최소 시간 실측** | 불필요 — 설계 전용, G2 구축 성공 여부는 04-02에서 확인 |
| **GPU OFF-2 · 분석/기록** | EKS 실제 구성과 예상 차이 및 IAM·네트워크 근거 분석 |

GPU가 필요한 실측은 각 세션에서 이미 준비된 명령·성공 기준·결과 저장 경로를 사용한다. 실패하면 원인 계층과 시간을 기록하고 사전 중단 조건을 적용한다.

## 운영 요구사항

단일 GPU 서버의 데이터·권한 흐름을 이해한 뒤에야 GPU Worker/Pod/EKS API의 접근 경로를 추가로 설계할 수 있다.

## G2 확정 네트워크 설계 (2026-11-25, GPU OFF)

**채택: 혼합형 egress.** 2개 AZ에 Private Subnet(CPU·GPU Node)을 두고, Public Subnet 하나에 **Public NAT Gateway 1개 + Elastic IP**를 배치한다. Private Subnet 라우팅 테이블에는 기본 경로 `0.0.0.0/0 → NAT Gateway`와 **S3 Gateway VPC Endpoint 경로**(서비스 prefix list `pl-… → vpce-…`)를 함께 구성한다. **두 Private Subnet의 라우팅 테이블을 S3 Endpoint에 연결해야** 모든 GPU Worker와 CPU Node에서 적용된다.

| 통신 | 기본 경로 | 검증 내용 |
|---|---|---|
| kubelet → Kubernetes API | EKS **private endpoint**, VPC 사설 경로 | Private DNS, API 접근, SG 허용 |
| GPU/CPU Node → S3 | **S3 Gateway VPC Endpoint** | Private route tables association, S3 prefix list route, IAM 및 endpoint/bucket policy |
| GPU/CPU Node → ECR 및 외부 레지스트리 | **NAT Gateway** (초기 설계) | 프라이빗 노드의 ECR 인증·레이어 다운로드(일부 레이어 S3 경유), 이미지 Pull |
| GPU/CPU Node → 기타 AWS Public API/인터넷 | **NAT Gateway** | IAM, SG egress, NAT 가용성, DNS |

**경로 선택 이유:** S3 목적지 Prefix List 경로가 기본 경로 `0.0.0.0/0`보다 우선해 S3 데이터셋 다운로드와 Checkpoint 업로드에 NAT 데이터 처리 요금을 발생시키지 않는다. **S3 Gateway Endpoint 자체에는 시간당/데이터 처리 요금이 없으나 S3 저장/요청 등 기본 서비스 요금은 별도**다. ECR Interface Endpoint(`ecr.api`, `ecr.dkr`)는 **초기 필수가 아니라 후속 비용/보안 최적화 후보**다.

**가용성/비용 제약:** NAT 1개는 개발용 비용 절감 설계이며 해당 AZ 장애 시 외부 egress가 중단될 수 있고 다른 AZ에서 NAT로 가는 트래픽에는 AZ 간 전송 요금 가능성이 있다. NAT 시간당 과금, EIP/공인 IPv4, 데이터 처리량과 EKS Control Plane/EC2/EBS/S3 비용을 실행 전에 계산하고 `terraform destroy` 및 잔여 EIP·ENI·NAT·볼륨 검증 절차를 준비한다. NAT 생성만으로 Kubernetes API private endpoint가 자동 설정되는 것은 아니다. 학습용 로컬 `kubectl` 접근 방식(제한된 public endpoint 또는 VPN/SSM 등 사설 접근 경로)은 G2 ON 전에 별도 결정한다.

**상태 (2026-11-26):** 네트워크 아키텍처 결정 및 `infra/g2/{versions,variables,network,outputs}.tf` 코드 작성 완료. 로컬 Terraform init/fmt/validate·plan, AWS 실제 생성·연결 검증은 **아직 사용자 실행 결과가 없다**. [G2 인수인계](../handoffs/g2-terraform-2026-11-26.md).

## 내부 동작

`Terraform VPC/Subnet/Route/SG → EKS API endpoint + EKS Node IAM role → EC2 GPU Worker + S3/ECR access`

## 학습·실습 순서

1. G1에서 사용한 서브넷·S3·IAM/SG 구조를 기준으로 EKS API, CPU 시스템 노드, GPU Worker의 연결 경로를 추가한 구조도 작성.
2. 채택된 **NAT 1개 + S3 Gateway Endpoint** 라우팅, private EKS endpoint, ECR Pull, SG·IAM 권한과 DNS의 책임을 구분.
3. Terraform 구성에서 서브넷 태그·nodegroup 역할·최소 IAM 권한·GPU Worker 이미지 레지스트리 접근 방법 설명.
4. 실행 없이 `terraform fmt`, `terraform validate`, `terraform plan` 가능한 범위로 검증하며 실제 환경/프로바이더 준비에 따라 plan 제약 명시.
5. EKS Control Plane·CPU 노드·GPU 2대·EBS·NAT·IPv4 비용 및 destroy 시 남는 자원 예상.

## 완료 증거

AWS 네트워크 데이터·제어 경로 그림, IAM 정책 검토, Terraform 계획·비용 게이트.

실제 실행 전에는 결과·복구·사용률을 만들어내지 않는다. AWS GPU 8 vCPU 쿼터는 승인됐지만 AZ 용량과 실제 실행 비용·동작은 별도 검증이 필요하다.
