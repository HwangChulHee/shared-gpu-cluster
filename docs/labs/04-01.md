# Lab 04-01 — EKS 확장에 필요한 VPC·IAM·네트워크 설계

> **2026-11-13 개편 · GPU Linux 서버에서 EKS로 확장** · 환경: L/O. **실제 EKS GPU 실습 미수행**. [Lab 이관](../migration-2026-11-13.md) 및 [운영 비용 게이트](../operations.md) 참조.

## GPU 비용 최적화 실행 구간

> 공통 기준: [GPU 실행 게이트·G1/G2 런북](../gpu-execution-gates.md). **OFF 준비가 완료되어도 GPU 실측을 완료한 것은 아니다.** 실제 출력과 가설/계획을 구분한다.

| 구간 | 수행할 작업·완료 기준 |
|---|---|
| **GPU OFF-1 · 사전 학습/로컬 검증** | G1 경험을 기반으로 EKS VPC·API/노드·ECR/S3·IAM·NAT/Endpoint 설계, Terraform fmt/validate/plan·비용/정리 계획 |
| **GPU ON · 최소 시간 실측** | 불필요 — 설계 전용, G2 구축 성공 여부는 04-02에서 확인 |
| **GPU OFF-2 · 분석/기록** | EKS 실제 구성과 예상 차이 및 IAM·네트워크 근거 분석 |

GPU가 필요한 실측은 각 세션에서 이미 준비된 명령·성공 기준·결과 저장 경로를 사용한다. 실패하면 원인 계층과 시간을 기록하고 사전 중단 조건을 적용한다.

## 운영 요구사항

단일 GPU 서버의 데이터·권한 흐름을 이해한 뒤에야 GPU Worker/Pod/EKS API의 접근 경로를 추가로 설계할 수 있다.

## 내부 동작

`Terraform VPC/Subnet/Route/SG → EKS API endpoint + EKS Node IAM role → EC2 GPU Worker + S3/ECR access`

## 학습·실습 순서

1. G1에서 사용한 서브넷·S3·IAM/SG 구조를 기준으로 EKS API, CPU 시스템 노드, GPU Worker의 연결 경로를 추가한 구조도 작성.
2. private/public endpoint, NAT/VPC Endpoint, ECR 이미지·S3 데이터 접근, SG·IAM 권한과 DNS의 책임을 구분.
3. Terraform 구성에서 서브넷 태그·nodegroup 역할·최소 IAM 권한·GPU Worker 이미지 레지스트리 접근 방법 설명.
4. 실행 없이 `terraform fmt`, `terraform validate`, `terraform plan` 가능한 범위로 검증하며 실제 환경/프로바이더 준비에 따라 plan 제약 명시.
5. EKS Control Plane·CPU 노드·GPU 2대·EBS·NAT·IPv4 비용 및 destroy 시 남는 자원 예상.

## 완료 증거

AWS 네트워크 데이터·제어 경로 그림, IAM 정책 검토, Terraform 계획·비용 게이트.

실제 실행 전에는 결과·복구·사용률을 만들어내지 않는다. AWS GPU 8 vCPU 쿼터는 승인됐지만 AZ 용량과 실제 실행 비용·동작은 별도 검증이 필요하다.

## 서술형 인출 문제

G1에서는 S3 데이터를 내려받았는데 EKS 프라이빗 GPU Worker에서 실패한다면 어떤 네트워크·IAM 계층을 추가로 확인해야 할까?
