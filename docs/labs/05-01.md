# Lab 05-01 — GPU Job 스케줄링·수명주기

> **새 7 Phase / 21 Lab 교안, 미실측** · 환경: G2. 동일 번호를 사용한 이전 교안과 학습 기록은 [이관표](../migration-2026-11-13.md) 참조.

## GPU 비용 최적화 실행 구간

> 공통 기준: [GPU 실행 게이트·G1/G2 런북](../gpu-execution-gates.md). **OFF 준비를 GPU 실측 완료로 간주하지 않는다.**

| 구간 | 수행할 작업·완료 기준 |
|---|---|
| **GPU OFF-1 · 사전 학습/로컬 검증** | GPU Worker 2대·Job 3개 요청량/배치 예상, Pending·반환 흐름·이벤트 관측 명령/스크립트 준비 |
| **GPU ON · 최소 시간 실측** | G2 두 Job 실행·한 Job 대기·GPU 반환 후 스케줄링 검증 |
| **GPU OFF-2 · 분석/기록** | Job/Pod/Node 타임라인 분석 |

GPU가 필요한 실측은 사전에 준비한 명령·성공 기준·보존 경로에 따라 실행한다. 실패하면 진단 시간·비용 상한을 적용하고 후속 실험을 멈춘다.

## 학습 목표·왜 필요한가

기본 kube-scheduler는 nvidia.com/gpu 요청과 노드 가용량/제약에 따라 Pod를 배치한다.

## 내부 동작·구성 요소

Job 생성→Pod 생성→Scheduler Filter/Bind→GPU 실행→완료→GPU 반환.

## 실무 시나리오

GPU 노드 2대에서 YOLO Job 3개 제출 시 Pending/실행/완료/반환을 기록한다.

## 준비·실습 (실제 사용자가 실행)

1. **사전 분석:** 위 시나리오의 운영 요구사항과 예상 실패 계층을 서술한다.
2. **비용 게이트:** 환경 G2. G1/G2가 포함될 경우 먼저 AWS GPU 쿼터 승인, EC2/EKS/네트워크/스토리지 비용, 생성·삭제 경로를 확인한다. 쿼터 8 vCPU는 승인·적용 확인됐지만 실제 AZ 용량·비용·AMI 준비 전에는 GPU를 실행하지 않는다.
3. **실행 준비:** AMI/Driver/CUDA/컨테이너, YOLO·데이터셋, Batch/Epoch, seed, 캐시 상태를 고정한다. 실행 명령은 실제 버전과 환경을 확인한 뒤 단계별로 확정한다.
4. **실행:** GPU 노드 2대에서 YOLO Job 3개 제출 시 Pending/실행/완료/반환을 기록한다.
5. **관측·분석:** 정상 기준선을 먼저 기록한 뒤 GPU·CPU·RAM·스토리지·Pod/Job Events 중 관련 지표를 수집한다. 대조군, 예상/실측, 반증 조건, 통제된 실패 주입 여부를 구분한다.
6. **정리:** 결과/Checkpoint 보존, Terraform/EC2/EKS/NAT/EBS/S3 잔여 과금 자원 점검.

## 완료 증거

kubectl Events, Pod 배치 노드, GPU 할당·실사용 지표.

실측이 없다면 계획 단계로 남긴다. [실제 사례·공식 근거](https://kubernetes.io/docs/concepts/scheduling-eviction/kube-scheduler/)는 출처 유형을 분리해서 기록하며, 장애 주입을 자연 발생 장애처럼 표현하지 않는다.

## 서술형 점검 (하나씩 진행)

GPU 요청 Job은 Pending인데 GPU Util이 0%인 상황은 왜 가능한가?
