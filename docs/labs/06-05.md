## 이 Lab을 배우는 이유

Pod Pending이 늘어났다고 GPU Scheduler만 원인으로 지목하면 Worker 장애와 가용 GPU 감소라는 상위 원인을 놓친다.

## 핵심 개념과 내부 원리

1. 복합 장애는 여러 구성 요소가 동시에 고장 난 상황만을 의미하지 않는다. GPU 용량 포화 상태에서 Worker 하나를 잃으면 자원 부족으로 작업 대기와 서비스 영향이 확대될 수 있다.

2. RCA는 '노드를 다시 시작했다'는 조치 목록이 아니라 관측 증거로 장애의 발생 원인·영향 경로·대응의 한계를 설명하는 문서다.

3. Runbook은 사고 발생 시 점검 순서와 안전한 복구 명령, 복구 확인 기준, 중단·에스컬레이션 조건을 반복 가능하게 작성한다.

## 시스템 동작 흐름

2 GPU 작업 점유 + 대기 Job → Worker 장애 주입 → Node/GPU/Job/사용자 현상 타임라인 → 대응/재발 방지 → 동일 부하로 복구 후 재검증 → RCA·Runbook.

## 실습 전 준비

T02 정상 측정치와 F01 단일 장애 실험, 안정화된 Kueue/영속 저장 경로, 실험 종료 및 리소스 삭제 절차 확보.

## 직접 실습

1. 두 GPU를 점유시키고 세 번째 팀 작업을 대기시킨다.
2. 한 GPU Worker를 중단하고 사건 시각별 Node/Job/서비스 메트릭과 사용자 영향 기록.
3. 복구 후 동등한 시나리오를 재실행하고 탐지시간·복구시간·실제 작업 손실·개선안을 RCA/Runbook으로 작성.

## 검증 기준과 남길 증거

- 사건 타임라인, 근본 원인, 사용자 영향, 완화·재발 방지 근거
- 자동 고가용성을 거짓 주장하지 않음

## 서술형 인출 질문

1. 노드 복구 완료와 서비스 정상화까지의 간격을 줄이려면 어떤 설계가 필요한가?
2. RCA와 Runbook은 어떤 목적과 독자를 가진 문서인가?
