# Lab 02-01 — AWS 네트워크·권한

> **학습 교안 / 미실행**. 실행 절차는 실제 AWS/패키지 버전에 맞춰 고정한 뒤 수행합니다. 예상 결과는 실측 결과가 아닙니다.

## 학습 맥락과 목표

노드가 Ready가 아니면 단순히 노드 사양만 의심하지 말고 IAM Role·DNS·API Endpoint·ECR 접근 경로를 순서대로 확인한다.

## 핵심 개념·원리

1. EKS 노드가 프라이빗 서브넷에 있더라도 이미지 다운로드·AWS API 접근에는 NAT 또는 VPC Endpoint 등 통신 경로가 필요하다. 노드의 인터넷 접근 가능 여부와 Kubernetes API Endpoint 접근 방식은 따로 결정한다.

2. VPC 서브넷·라우팅·보안 그룹은 네트워크 계층의 통신을 제어한다. IAM은 AWS API 작업 권한을 제어한다. 보안 그룹만 허용했다고 IAM 권한 문제가 해결되지 않는다.

3. Terraform plan은 의도된 변경 내용을 검토하는 도구이지 실제 연결성 성공을 보장하지 않는다. EKS 생성 전 네트워크·권한 검증을 수행해야 한다.

## 내부 흐름

VPC/서브넷/라우트 준비 → EKS Cluster/IAM 권한 → 노드 VPC 연결 → 이미지 레지스트리/AWS 서비스 접근 → Kubernetes API 및 Pod 트래픽 검증.

## 실습 준비

AWS 계정, Terraform 버전, 상태 저장 위치와 비밀정보 관리 방침. 단일 AZ/멀티 AZ 비용 및 가용성 차이 기록.

## 실습

1. VPC와 Public/Private Subnet, 라우팅, NAT/Endpoint 후보를 표로 설계한다.
2. Terraform validate/plan으로 리소스·참조 관계를 확인한다.
3. 실제 클러스터 구축 시 연결성 문제에 대비해 IAM·SG·DNS·라우트 진단 체크리스트를 만든다.

## 검증할 증거

- 네트워크 다이어그램에서 인터넷/사설망/Kubernetes API 경로 구분
- Terraform plan과 연결성 테스트를 혼동하지 않음

## 서술형 인출 질문

1. 프라이빗 노드가 ECR 이미지를 Pull하지 못할 때 확인할 계층은?
2. IAM Role과 Security Group은 어떤 다른 문제를 해결하는가?
