# Lab 02-01 — Linux GPU 서버의 시스템 운영·진단

> **2026-11-13 Linux GPU 서버 중심 교안** · 환경: **L+G1** · 실제 GPU 실험 미완료. [이관표](../migration-2026-11-13.md)에서 이전 번호를 확인한다.

## 실제 운영 요구와 학습 목적

GPU가 정상이라도 Linux 호스트의 CPU·RAM·스토리지·프로세스 제한으로 학습은 실패하거나 느려질 수 있다. GPU 서버 엔지니어에게 호스트 관측은 기본이다.

## 내부 동작·책임 분리

`YOLO 프로세스 → CPU 스레드/파일 I/O/페이지 캐시 → RAM·디스크 → GPU Driver/VRAM`

## 학습 및 직접 실습

1. GPU를 켜기 전에 Linux 프로세스·PID/스레드, CPU 사용률, load average, RSS와 캐시, 파일 디스크/마운트, journal 로그를 구분한다.
2. G1에서 `uname -a`, `lscpu`, `free -h`, `lsblk`, `df -h`, `ps -eo pid,comm,%cpu,%mem --sort=-%cpu`, `top`을 사용해 호스트 기준선 기록.
3. YOLO 학습 전/도중 CPU·메모리·디스크 활동 비교. `iostat`(sysstat이 있을 때), `journalctl`(지원되는 OS/권한에서)으로 로그·I/O를 확인.
4. CPU/RAM 사용량이 높을 때 GPU VRAM OOM과 Linux OOM, 파일시스템 공간 부족을 각각 어떻게 구분할지 기록.
5. **운영 자동화 기초:** Bash 또는 Python으로 GPU/CPU/RAM/디스크/프로세스 상태를 수집하는 작은 진단 스크립트를 만들고, 오류 코드·로그·반복 실행 결과를 남긴다.
6. 로그와 결과 보존 후 GPU 종료/잔여 리소스 점검.

## 완료 판정에 필요한 실제 증거

GPU 호스트 OS 버전, CPU·RAM·프로세스/디스크 상태, 학습 전후 변화와 해석, **Bash/Python 진단 스크립트와 실제 출력**.

GPU/EKS 실행 전 **G/VT 쿼터 8 vCPU 적용 확인**과 별도로 EC2 AZ 용량·AMI·실제 가격·EBS/S3/NAT/IPv4 부대 비용·리소스 삭제 계획을 검토한다. 준비되지 않으면 L 이론만 진행하고 GPU 실습은 **대기**로 표시한다. 예상과 실제 출력은 구분한다.
