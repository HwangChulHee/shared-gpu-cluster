# Lab 03-02 — 부서별 격리·정책

> **학습 교안 / 미실행**. 실행 절차는 실제 AWS/패키지 버전에 맞춰 고정한 뒤 수행합니다. 예상 결과는 실측 결과가 아닙니다.

## 학습 맥락과 목표

팀 A의 GPU 쿼터가 1이고 다른 팀이 유휴라고 해서 팀 A가 자동으로 2개 GPU를 얻지는 않는다. 공유 풀의 정책은 quota와 queue 설정을 구분해 설계한다.

## 핵심 개념·원리

1. Namespace는 Kubernetes 오브젝트 관리 경계이며, 자체만으로 강력한 보안 격리를 보장하지 않는다. RBAC와 네트워크 정책, 신뢰할 수 있는 사용자 식별이 함께 필요하다.

2. ResourceQuota는 네임스페이스에서 사용할 수 있는 자원·객체량을 제한한다. GPU 확장 자원 Quota를 설정할 수 있지만 다른 팀으로 남는 할당량을 자동 대여하는 공정 큐 역할은 아니다.

3. PriorityClass는 Pod 스케줄링과 선점에 영향을 주지만, 실행 중 GPU 학습을 선점하면 작업 손실이 클 수 있다. 공정성·중요도·복구 비용을 함께 고려해야 한다.

## 내부 흐름

팀 신원 확인 → 허용된 Namespace/ResourceQuota/RBAC 적용 → Job 제출 허용 여부 → Scheduler 자원 배치 → 실행 중 정책 위반 여부 관찰.

## 실습 준비

Namespace A/B/C와 제한된 서비스 계정, 테스트할 Job 요청 수 및 GPU Quota 값을 명시.

## 실습

1. 팀 A/B/C 별도 Namespace와 RBAC/ResourceQuota 생성.
2. 팀 A GPU Quota 초과 Job 제출 시 API 거절 또는 실행 제한 결과 조사.
3. 허용된 팀 작업만 읽을 수 있는지 권한 검증. PriorityClass 적용 시 효과와 리스크 기록.

## 검증할 증거

- RBAC 오류, Quota 거절, Pod Pending을 서로 다른 현상으로 구별
- 다른 팀 접근 시도가 서버에서 거절되는지 검증

## 서술형 인출 질문

1. RBAC 403 오류와 GPU 부족에 따른 Pod Pending은 어떻게 다른가?
2. ResourceQuota만으로 부서 간 공정한 GPU 대여가 보장되지 않는 이유는?
