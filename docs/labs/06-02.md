# Lab 06-02 — 데이터 로딩 병목 재현·개선 (대조 실험)

> 새 21 Lab · 실측 전 · 환경 **G1** · [03-03 정상 성능 기준선](03-03.md)이 선행 조건.
>
> **범위 구분:** 02-03에서 DataLoader 기본 동작을 익히고 03-03에서 정상 기준선을 확보했다면 이 Lab에서는 **실제 AWS 성능 실험을 참고해 병목 가설을 검증하고 개선 전후를 비교**한다.

## GPU 비용 최적화 실행 구간

> 공통 기준: [GPU 실행 게이트·G1/G2 런북](../gpu-execution-gates.md). **OFF 준비를 GPU 실측 완료로 간주하지 않는다.**

| 구간 | 수행할 작업·완료 기준 |
|---|---|
| **GPU OFF-1 · 사전 학습/로컬 검증** | workers/cache/전처리/로컬 EBS 입력 이론, 충분한 benchmark 데이터·반복 실험 조건·측정 스크립트 준비; 03-03 baseline 재사용 |
| **GPU ON · 최소 시간 실측** | G1 고정 설정의 A/B 실험·메트릭 수집, 한 변수씩 변경 |
| **GPU OFF-2 · 분석/기록** | 성능 개선/미개선 포함한 평균·편차·병목 가설 검토 |

GPU가 필요한 실측은 사전에 준비한 명령·성공 기준·보존 경로에 따라 실행한다. 실패하면 진단 시간·비용 상한을 적용하고 후속 실험을 멈춘다.

## 실제 사례와 가설

[AWS 데이터 로딩 성능 실험](https://aws.amazon.com/blogs/machine-learning/applying-data-loading-best-practices-for-ml-training-with-amazon-s3-clients/)은 이미지 공급 경로와 로더 병렬도가 GPU 공급 속도에 영향을 줄 수 있음을 보여주는 **실제 성능 실험**이다. 원문 데이터셋/하드웨어의 측정치를 이 프로젝트의 결과처럼 사용하지 않는다.

**가설:** 이미지 입출력이나 CPU 전처리가 병목이라면 데이터를 로컬에 미리 준비하거나 적절하게 로더 병렬도를 설정할 때 YOLO의 처리량·학습시간이 개선될 수 있다.

**반증:** GPU 연산 포화 또는 전처리 비중이 작다면 로더를 바꿔도 의미 있게 개선되지 않을 수 있다.

## 내부 경로

`S3 원본 → 네트워크/객체 요청 → 로컬 캐시(EBS) → DataLoader worker/CPU decoder → batch → GPU`

스토리지 전송 지연, CPU 디코딩 시간, GPU 연산 시간과 체크포인트 쓰기 시간을 분리해서 해석한다.

## 비교 실험 계약 — GPU OFF-1에 확정

- **기본 비교 B (DataLoader):** `workers=0` 대 `workers=2`를 *초기 후보*로 설정. g6.xlarge는 4 vCPU이므로 workers=8은 필수 비교가 아니다. `batch/imgsz/epochs/cache/seed/데이터/스토리지`는 고정. 실제 2 worker 지원과 리소스 한도는 로컬 및 G1에서 확인하고 기록한다.
- **독립 비교 A (입력 준비):** S3→EBS 다운로드 소요시간 + EBS에서 YOLO 학습시간을 **각각 계측**. 직접 S3 객체를 DataLoader가 읽는 지원 경로가 검증되지 않으면 'S3 직접 학습'으로 표기하지 않는다. DataLoader B 비교와 A의 입력 전송 측정 결과를 하나의 단일 변수 효과로 혼합하지 않는다.
- **반복·지표:** 조건당 3회 지향(비용 시 횟수 사전 축소·사유 명시), Run ID/설정 JSON, CPU 사용률·RAM·GPU Util/VRAM·디스크 읽기/처리량, 전체/epoch 시간. cache warm 여부는 독립 기록하고 표본 구간을 맞춘다.
- **성공/중단 기준:** 03-03 정상 기준선과 메트릭 수집 정상일 때만 변경 조건 시작; CUDA OOM/호스트 메모리 압박/데이터셋 누락·실험 설정 불일치 발생 시 후속 비교 중단. 개선이 없으면 '미개선'을 정상적인 결과로 기록.
- **결과:** 동일 조건 raw 로그와 최소 summary CSV(조건, 반복, 이미지 수, wall 시간, epoch 시간, images/s, GPU/CPU·I/O 요약, 실패 여부)를 S3에 보존하고 OFF-2에서 평균/편차·조건 차이를 해석한다.

## 실습 계획 (**G1 세션 종료 전**, GPU 실행 준비 완료 후)

1. **사전 준비:** [02-03 DataLoader 기초](02-03.md) 및 [03-03 성능 기준선](03-03.md)의 모델·데이터셋·배치·Epoch·GPU·드라이버·이미지 버전을 고정하고 사용 시간을 예산에 반영한다.
2. **실험 A — 입력 경로:** 같은 데이터에 대해 로컬 EBS 파일을 사용하는 조건과 S3 입력을 준비하는 조건을 비교한다. 직접 S3 객체를 YOLO 데이터 로더로 읽는 방식은 별도 구현/지원이 검증되었을 때만 측정; 그렇지 않으면 **사전 다운로드 시간과 학습시간을 별도로** 측정한다.
3. **실험 B — CPU 병렬도:** 같은 로컬 데이터로 `workers=0` 및 제한된 `workers>0` 설정을 비교. 동시에 `cache` 및 `batch`는 고정.
4. 조건별 3회 이상 반복을 목표로 하고, 콜드·웜 캐시, CPU/RAM 사용, GPU Util·VRAM, images/s, Epoch 시간과 I/O 시간 기록.
5. 결과가 개선되지 않더라도 그대로 기록하고, 병목 가설을 반박하거나 다른 제한 요인을 설명한다.
6. **Phase 03의 G1 세션에서 이어서 수행하고 GPU를 재구축하지 않는다.** 실험 데이터·로그 보존 후 GPU 자원과 잔여 AWS 과금 확인.

## 완료 증거

조건별 측정표/그래프, 동일 조건 반복 결과, 개선 또는 미개선 원인 분석, 실제 AWS 사례와 다른 점, 실행 명령·설정·로그.
