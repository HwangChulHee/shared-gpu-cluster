# Lab 06-02 — GPU Worker 장애와 Job 복구

> **학습 교안 / 실행 전**. 아래 예시는 실제 테스트 결과가 아닙니다.

## 이 Lab을 배우는 이유

노드 교체까지 5분이 걸리고 학습 Pod가 2분 뒤 재개하더라도 작업이 checkpoint 없이 처음부터 시작하면 최종 복구 손실은 더 커진다.

## 핵심 개념과 내부 원리

1. Kubernetes Node NotReady는 Kubernetes가 관찰한 상태이며 실제 EC2 교체·GPU 인식·모델 서비스 가용성 회복과 시점이 다르다.

2. Kubernetes Job은 실패/종료된 Pod를 조건에 따라 재생성할 수 있으나 체크포인트에서 학습을 재개할지는 애플리케이션 설정과 외부 저장소가 결정한다.

3. GPU가 2개 모두 할당된 상태에서 한 Worker가 중단되면 남은 GPU에 여유가 없어 즉시 재배치되지 않을 수 있다. 고가용성 용량 계획과 단순 자동 치유를 구분해야 한다.

## 시스템 동작 흐름

정상 기준선 → GPU Worker 중단 주입 → Node/Pod 감지 → 관리형 Node Group의 복구 여부 관찰 → 새 GPU 등록 → Job 재실행 → S3 체크포인트 재개 → 사용자 서비스 확인.

## 실습 전 준비

테스트 전 S3 체크포인트를 실제로 다운로드·재개 가능한지 확인. NodeGroup 복구 설정과 지원 범위 확인, 안전한 통제된 중단 방식 결정.

## 직접 실습

1. YOLO 학습 중 해당 GPU Node를 격리된 실습 환경에서 통제된 방법으로 중단.
2. Node Ready/NotReady, Pod/Job 상태, 새 노드의 GPU 자원 등록까지 시간 기록.
3. 기존 체크포인트에서 학습 재개와 처음부터 재실행을 비교. 다른 팀 Gemma/XGBoost 영향 별도 측정.

## 검증 기준과 남길 증거

- 감지·노드 용량 회복·GPU 등록·작업 재개·사용자 복구를 구분한 타임라인
- 관리형 서비스의 자동 복구 여부를 관찰 사실로만 기록

## 서술형 인출 질문

1. 노드가 Ready로 돌아왔는데 사용자 서비스가 여전히 실패할 수 있는 이유는?
2. Pod 재생성과 체크포인트 재개를 분리 측정해야 하는 이유는?
