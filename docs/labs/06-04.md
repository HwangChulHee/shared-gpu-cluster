# Lab 06-04 — 스토리지 병목·GPU 공정성 장애

> **학습 교안 / 실행 전**. 아래 예시는 실제 테스트 결과가 아닙니다.

## 이 Lab을 배우는 이유

GPU 사용률이 20%인데 YOLO 학습시간만 길어졌다면 스토리지 I/O와 CPU 데이터 로더를 확인한다. GPU 사용률이 높아도 다른 부서가 무기한 기다리면 공정성 실패일 수 있다.

## 핵심 개념과 내부 원리

1. GPU 학습이 느린 원인은 GPU 계산, 데이터 로딩, 스토리지 네트워크 I/O, CPU 전처리 중 어디에나 있을 수 있다. 메트릭을 결합해 병목을 좁혀야 한다.

2. 의도적으로 I/O를 제한해 재현한 성능 저하는 실제 스토리지 장애와 다른 사건이다. 실험 기록에서 원인 주입 방법을 공개해야 한다.

3. 특정 팀의 장기 대기는 장비 장애가 아니라 자원 할당·공정성 정책 문제일 수 있다. Quota와 Kueue가 사용자 대기시간에 미치는 효과를 동일 제출 패턴으로 비교한다.

## 시스템 동작 흐름

정상 데이터 경로/기본 큐 정책 측정 → 입력 I/O 또는 부서 제출 패턴 변경 → GPU Util·Job 대기·데이터 로딩 시간 관측 → 개선 정책/캐시 적용 → 동일 조건 재측정.

## 실습 전 준비

동일한 모델·epoch·배치·데이터셋·GPU와 작업 제출 순서 유지. 통제할 I/O 지연/큐 정책을 한 번에 하나씩 변경.

## 직접 실습

1. 동일 YOLO 작업에서 S3 다운로드+캐시와 조절된 입력 지연 조건의 학습시간 비교.
2. 팀 A가 작업을 다수 제출한 경우 팀 B/C의 대기시간 측정.
3. Kueue 할당량/borrow 정책으로 동일 제출 부하 재실험하고 공정성/처리량 비교.

## 검증 기준과 남길 증거

- 병목의 인과관계를 단일 변수 변경으로 입증
- 장비 장애와 운영 정책 문제를 분리 보고

## 서술형 인출 질문

1. GPU Util이 낮고 학습시간이 긴 경우 어떤 측정값으로 I/O 병목을 증명할 것인가?
2. 한 팀의 작업만 빨리 끝나고 나머지 팀이 오래 대기할 때 어떤 정책 지표가 필요한가?
