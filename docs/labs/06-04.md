# Lab 06-04 — GPU Worker 중단·Job 복구

> **새 7 Phase / 21 Lab 교안, 미실측** · 환경: G2. 동일 번호를 사용한 이전 교안과 학습 기록은 [이관표](../migration-2026-11-13.md) 참조.

## GPU 비용 최적화 실행 구간

> 공통 기준: [GPU 실행 게이트·G1/G2 런북](../gpu-execution-gates.md). **OFF 준비를 GPU 실측 완료로 간주하지 않는다.**

| 구간 | 수행할 작업·완료 기준 |
|---|---|
| **GPU OFF-1 · 사전 학습/로컬 검증** | Node/Job/앱 resume 구별, GPU Worker 중단·복원 이벤트 계측 스크립트 및 S3 checkpoint 백업 검증 |
| **GPU ON · 최소 시간 실측** | G2 GPU Worker 통제 중단 후 Node Ready/Job 상태/YOLO resume 단계별 관측 |
| **GPU OFF-2 · 분석/기록** | 타임라인·재학습량·RCA·복구 한계 정리 |

GPU가 필요한 실측은 사전에 준비한 명령·성공 기준·보존 경로에 따라 실행한다. 실패하면 진단 시간·비용 상한을 적용하고 후속 실험을 멈춘다.

## 학습 목표·왜 필요한가

Node 교체, GPU 자원 재등록, Job 재실행, YOLO resume은 서로 다른 동작이다.

## 내부 동작·구성 요소

Node 장애→K8s 감지→용량 회복→GPU 등록→Job 실행→앱 Resume.

## 실무 시나리오

격리 노드를 통제 종료해 복구 타임라인과 잔여 GPU 부족 시 Pending을 관찰한다. **G2 클러스터 실습 도중 실시하고, 중단 정책·Node Group 교체시간·Job 재실행과 YOLO의 앱 수준 resume을 각각 분리 측정**한다.

## Worker 장애 실험 계약 — GPU OFF-1에 확정

1. **사전 조건:** G2의 정상 2 GPU 등록, YOLO Job의 정상 실행, S3에 **optimizer/학습 재개 상태 포함 checkpoint** 존재와 복원 방법 확인, 원본 로그/Events 수집 준비.
2. **쿼터 한계:** GPU Worker 2대 = 8 vCPU. 하나를 종료해도 교체 노드가 즉시 생긴다고 보장할 수 없다. **EC2 실제 종료/쿼터 해제 → 새 인스턴스 Capacity 확보 → Node Ready → GPU Plugin 등록**의 별도 단계로 시간과 결과를 측정한다.
3. **실패 시 동작:** K8s Job `backoffLimit`, `restartPolicy`, 재생성 조건, 노드 NotReady·Pod 삭제/대기 조건을 사전 정의한다. **Kubernetes Job 복구와 YOLO의 checkpoint resume은 독립적**이고, GPU 대기 자원이 없으면 새 Pod가 Pending일 수 있다.
4. **안전:** 실험할 Worker/Job을 지정하고 데이터 보존·복구/중단 명령과 예산·타임아웃을 검토. 대체 노드가 생성되지 않거나 checkpoint가 없으면 무리하게 진행하지 않고 정리.
5. **필수 증거:** EC2/Node/Pod/Job 이벤트 및 UTC 시각, GPU Allocatable, checkpoint S3 키·업/다운로드 해시, YOLO 시작/재개 epoch, 실패/성공 경로. 정상 복구가 관측되지 않았다면 미복구로 기록한다.

## 준비·실습 (실제 사용자가 실행)

1. **사전 분석:** 위 시나리오의 운영 요구사항과 예상 실패 계층을 서술한다.
2. **비용 게이트:** 환경 G2. G1/G2가 포함될 경우 먼저 AWS GPU 쿼터 승인, EC2/EKS/네트워크/스토리지 비용, 생성·삭제 경로를 확인한다. 쿼터 8 vCPU는 승인·적용 확인됐지만 실제 AZ 용량·비용·AMI 준비 전에는 GPU를 실행하지 않는다.
3. **실행 준비:** AMI/Driver/CUDA/컨테이너, YOLO·데이터셋, Batch/Epoch, seed, 캐시 상태를 고정한다. 실행 명령은 실제 버전과 환경을 확인한 뒤 단계별로 확정한다.
4. **실행:** 격리 노드를 통제 종료해 복구 타임라인과 잔여 GPU 부족 시 Pending을 관찰한다.
5. **관측·분석:** 정상 기준선을 먼저 기록한 뒤 GPU·CPU·RAM·스토리지·Pod/Job Events 중 관련 지표를 수집한다. 대조군, 예상/실측, 반증 조건, 통제된 실패 주입 여부를 구분한다.
6. **정리:** 결과/Checkpoint 보존, Terraform/EC2/EKS/NAT/EBS/S3 잔여 과금 자원 점검.

## 완료 증거

Node/Job/Pod Events, 복구시간, 앱 재학습량, RCA.

실측이 없다면 계획 단계로 남긴다. [실제 사례·공식 근거](https://kubernetes.io/docs/concepts/workloads/controllers/job/)는 출처 유형을 분리해서 기록하며, 장애 주입을 자연 발생 장애처럼 표현하지 않는다.
