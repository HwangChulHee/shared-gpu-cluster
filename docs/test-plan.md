# 모니터링·성능·운영 장애 검증 계획

> **계획 문서**입니다. 아래 시나리오의 성공, 성능 수치 또는 자동 복구는 아직 검증되지 않았습니다.

## 관측 체계

| 범주 | 측정 항목 | 주요 데이터 출처 |
|---|---|---|
| GPU | GPU 사용률, VRAM 사용량, 온도/전력, GPU별 할당 현황 | DCGM exporter / K8s resource 상태 |
| K8s | Node Ready, Pod/Job phase, Pending 원인, 배치 노드, 재시작 횟수 | K8s API, Events, kube-state-metrics |
| 서비스 | Gemma 응답 지연/처리량, YOLO/XGBoost 실행 시간/성공률 | 서비스 및 Job 계측 로그 |
| 스케줄링 | 제출→승인→실행 지연, 팀별 대기시간, 할당·반환 | API 타임스탬프, Job/Kueue(도입 시) |
| 스토리지 | 읽기 처리량, 지연, 오류, 모델 로딩 시간 | fio 등 벤치마크, 애플리케이션 계측 |
| 운영 | 감지 시간, 영향 범위, 복구 시간, 재실행·체크포인트 손실 | 이벤트 타임라인 / Incident Report |

GPU 할당 여부와 GPU 연산 사용률은 다릅니다. DCGM만으로 서비스/Job 지표 전체를 제공한다고 가정하지 않습니다.

## 공통 대조 실험 조건

정책·부하·장애 전후에 **같은 GPU 인스턴스 종류, 모델/양자화, 데이터셋, 컨테이너 버전, 제출 순서, 동시성**을 유지합니다. 캐시/모델 로딩(콜드/웜), 노드 교체 및 AZ 차이는 따로 기록합니다. 시간 기준(제출·실행·종료, 장애 주입·감지·복구)을 일관되게 정의하고 동일 조건을 반복 실행합니다. 값이 개선되지 않아도 실제 관찰대로 기록합니다.

**기준선:** 모델별 개별 실행과 두 GPU/세 팀의 기본 스케줄링을 먼저 측정. **비교군:** ResourceQuota/Kueue 정책, 스토리지 조건 변경 및 장애 이후 회복 상태. 사용률만으로 공정성·가용성을 판단하지 않습니다.

## 정상·부하 실험

### T01 — 단일 팀 정상 작업
- 세 모델을 각각 동일 GPU 환경에서 반복 실행
- 예상: 성공 상태, GPU 사용/작업 메트릭 및 결과 출력
- 검증: 입력·모델 버전·컨테이너 이미지·시간·GPU 메모리·로그 기록, 냉/온 시작 여부와 3회 이상 반복 여부 명시

### T02 — 2 GPU에 3팀 동시 제출
- 종료 가능한 GPU Job 3개로 두 개의 GPU 점유와 세 번째 대기 유도
- 예상: 자원 반환 이후 대기 Job 실행. 정확한 배치 및 대기 시간은 측정 결과로 판단
- 검증: 기본 Scheduler의 Pod Pending/Events와 Kueue의 Workload 미승인·Job suspension을 **분리**해 기록. 적용 전후 동일 요청 GPU 수, 노드 배치, 대기 시간, 공정성 비교

### T03 — 부하와 운영 정책
- Gemma 동시 요청 또는 YOLO/XGBoost Job 제출량을 단계적으로 증가
- 예상: 대기시간/처리량 변화. GPU 메모리 부족·서비스 거절 조건 확인
- 검증: 요청/작업 수, P50/P95 지연, Job 처리량, GPU 사용률, 실패율
- 주의: 상시 Gemma 서비스와 배치 Job 동시 실행은 별도 정책 시나리오로 구분

## 장애 후보 (실측 전 최종 선정)

### F01 — GPU Worker 1대 장애와 작업 복구 (1순위)
- 동작 중인 GPU Worker 1대를 통제된 방법으로 중단
- 증거: 이벤트/노드 상태, GPU 할당 감소, 다른 팀의 작업 영향, 노드 보충 여부
- 검증: 노드 장애 감지 시간, 노드 용량 회복 시간, Job 재실행까지의 시간, **S3에 보존된 체크포인트에서 애플리케이션 수준으로 재개했는지**, 사용자 영향 각각 구분
- 주의: GPU 잔여 용량이 없으면 즉시 재스케줄링 불가능; 자동 노드 교체 여부/조건 사전 확인

### F02 — GPU 인식 실패 (후보)
- 지원되는 설정 범위에서 Device Plugin/Container Runtime 계층의 오류를 통제된 방식으로 재현
- 증거: 호스트 `nvidia-smi`, `nvidia.com/gpu` Capacity/Allocatable, Pod 상태와 로그
- 검증: GPU 등록 복원 및 정상 GPU Job 재실행
- 주의: 고의적인 드라이버 손상·GPU 하드웨어 고장 재현은 제외

### F03 — 공유 스토리지 지연 및 I/O 병목 (후보)
- 데이터 로딩과 학습 속도에 영향을 주는 조절 가능한 조건을 구성
- 증거: GPU Util, 모델 로딩/입력 지연, I/O 처리량 및 오류, Job 소요시간
- 검증: 조건 변경 전후 동일 데이터·모델·GPU에서 비교
- 주의: 실제 저장소 장애와 의도적 I/O 부하를 별도로 구분

### F04 — 부서별 GPU 자원 독점 / 장기 대기 (운영 정책 실험)
- 특정 팀이 작업을 집중 제출해 다른 팀의 GPU 작업이 밀리는 상황 관찰
- 증거: 팀별 대기·완료시간, GPU 할당, 큐 및 정책
- 검증: 기본 스케줄링 기준선 → Kueue admission/borrowing 정책 → 동일 제출 패턴 비교. Kueue 대기와 Pod Pending의 의미를 구분
- 주의: 장비 장애가 아니라 **운영 정책 문제**로 분류

## 종합 실험 — GPU 포화 중 Worker 장애

1. Gemma/YOLO/XGBoost의 GPU 수요와 실행 순서를 통제
2. GPU 2개를 점유시키고 다른 팀 작업은 대기하도록 구성
3. Worker 1대 중단, 영향 받은 Job 및 정상 Job 상태 확인
4. EKS 노드 용량 회복, GPU 재등록, Job 재실행/대기 상태 시간별 기록
5. 체크포인트 저장/미저장 여부에 따른 작업 손실 비교
6. 회복 후 정상 기준선 재검증 및 RCA 작성

**성공 기준은 장애를 무조건 무중단 복구하는 것이 아니라** 실제 지원된 자동 복구 범위를 정확히 관찰하고, 문제를 원인별로 분리·설명하는 것입니다.

입력: 모델, 데이터, 요청 수, Job 설정
