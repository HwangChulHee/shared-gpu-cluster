# Lab 01-03 — GPU 소프트웨어 스택

> 상태: 이론 완료 / 대기(GPU)
>
> 학습일: 2026-11-12 · 평가일: 2026-11-12 · 환경: L (이론/시나리오), G1 대기

## 목표와 사전 이해
- 호스트 GPU 드라이버, CUDA 런타임/툴킷, 프레임워크, NVIDIA Container Toolkit, Kubernetes Device Plugin 역할 구분
- 초기에는 CUDA Runtime과 CUDA Toolkit, NVIDIA Container Runtime 명칭을 혼동하여 추가 설명을 요청함

## 개념·내부 동작 요약
- NVIDIA Driver: 호스트 GPU 제어, CUDA Driver API 제공.
- CUDA Runtime 및 관련 GPU 라이브러리: 프레임워크의 GPU 연산 실행에 사용; 전체 CUDA Toolkit은 사전 빌드 프로그램 실행에 항상 필수는 아님.
- NVIDIA Container Toolkit: 컨테이너에 GPU 장치와 호스트 드라이버 라이브러리를 연결.
- Device Plugin: kubelet이 nvidia.com/gpu 확장 자원을 보고하고 장치 할당을 지원.
- nvidia-smi/NVML 정상 동작은 PyTorch CUDA 연산 성공의 충분조건이 아님.

## 서술형 인출
1. 호스트 Driver 정상, 호스트 CUDA Toolkit 없음, 컨테이너에 CUDA 런타임이 있다면 실행 가능한가?
   - 초기 답: 의존 관계상 전부 불가능하다고 판단.
   - 피드백: Toolkit 개발 패키지와 런타임 라이브러리를 구분하여 정정.
2. 컨테이너에 CUDA/PyTorch 있지만 호스트 Driver 부재 시?
   - 답: NVIDIA Driver 필요, Container Toolkit도 GPU 장치 연결에 필요.
   - 피드백: 정확. NVIDIA Container Runtime과 Toolkit 명칭의 차이 보완.
3. 호스트 nvidia-smi 성공, 컨테이너 실패 시?
   - 답: Driver보다 NVIDIA Container Toolkit 설정을 우선 확인.
   - 피드백: 정확. 호스트의 nvidia-smi만으로 CUDA 전체 호환성을 보장하지 않음.
4. K8s 노드에 GPU 자원이 등록되지 않았을 때?
   - 답: NVIDIA Device Plugin이 Kubernetes에서 GPU 인식을 돕는 구성 요소.
   - 피드백: 정확. kubelet의 확장 자원 보고 역할로 구체화.
5. 노드 GPU 등록 및 Pod 배치 정상인데 torch.cuda.is_available() false?
   - 답: Pod 내부 CUDA Runtime 이상 의심.
   - 피드백: 계층은 적절하게 지목했지만 단정할 수 없음. GPU 노출/CPU 전용 torch/드라이버 호환성 순서로 확인 필요.
