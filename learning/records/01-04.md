# Lab 01-04 — Gemma 4 추론

> 상태: 이론 완료 / 대기(GPU)
>
> 학습일: 2026-11-12 · 평가일: 2026-11-12 · 환경: L(이론/시나리오), G1 대기

## 목표와 사전 이해
- Gemma 4 E4B QAT W4A16 모델을 vLLM으로 운영할 때 모델 적재, Prefill/Decode, KV Cache, 메모리, 처리량·지연 지표의 역할 이해.
- 선수 개념: GPU/VRAM, CUDA 및 드라이버 계층.

## 개념·내부 동작 요약
- 모델 로딩: 파일 다운로드/스토리지 → CPU 측 처리 → GPU 가중치 적재. 모델 서버 상시 구동 시 매 요청마다 새로 로딩하지 않음.
- Prefill: 입력 토큰 처리. Decode: 출력 토큰 순차 생성. 첫 응답 지연과 이후 출력 속도는 구분.
- KV Cache: 이전 문맥의 key/value 텐서를 보존하여 반복 계산 절약. 동시 요청과 문맥 길이에 따라 VRAM 사용 증가.
- 4비트 가중치 양자화는 모든 VRAM 사용량을 4비트로 만드는 게 아니며 런타임·KV Cache 메모리 별도.
- GPU Utilization 95%는 계산 능력을 95% 모두 소진했다는 단정 근거는 아님. 요청 대기열·TTFT·TPOT·Tokens/s·메모리 사용을 함께 봐야 함.

## 서술형 인출 (실제 답변 근거)
1. 긴 문서에서 첫 토큰만 늦고 이후 속도가 정상인 이유?
   - 답: Decode 문제는 아니고 모델도 이미 적재되었으므로 Prefill 병목이 합리적.
   - 피드백: 정확. TTFT를 대기열/토큰화/Prefill로 세분 측정 필요.
2. 4비트 모델에서 동시 사용자 20명 시 VRAM 부족 원인과 대책?
   - 답: KV Cache 증가. PagedAttention, VRAM 확대 검토.
   - 피드백: 정확. PagedAttention은 실제 메모리 요구를 없애지 않으며 동시성·문맥 길이 제어도 중요.
3. 모델 GPU 적재 중 OS OOM Killer 기록, VRAM 충분한 이유?
   - 답: 모델 로딩 과정에서 CPU RAM 부족으로 실패.
   - 피드백: 정확. 실제 로그로 호스트/컨테이너 메모리 제한 및 타 프로세스도 확인 필요.
4. GPU Util 95%, VRAM 70%, 대기열 증가 시 우선 대응?
   - 답: 메모리 증설보다 GPU 처리 성능/동시 요청 제어를 우선 분석·개선.
   - 피드백: 정확. GPU Util 값만으로 완전한 계산 병목을 확정하지 않고 TTFT/TPOT/Tokens/s 확인.
