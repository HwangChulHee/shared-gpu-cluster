# Lab 01-05 — YOLO 이미지 학습

> 상태: 이론 완료 / 대기(GPU)
>
> 학습일: 2026-11-12 · 평가일: 2026-11-12 · 환경: L(이론/시나리오), G1 대기

## 목표와 사전 이해
- YOLO 학습의 Forward/Loss/Backward/Optimizer, Batch Size, Gradient Accumulation, Checkpoint, CPU/스토리지 병목을 이해.
- AWS G 계열 쿼터 승인 대기 중이므로 GPU 실습 없음.

## 개념·내부 동작 요약
- Batch Size 증가 시 입력 데이터와 학습 중간 Activation 저장량이 증가하며 VRAM OOM 가능. 모델 가중치 및 파라미터 Gradient 크기는 보통 Batch Size에 비례해 증가하지 않음.
- Gradient Accumulation: 작은 Micro-Batch의 Backward 후 Activation은 해제 가능하고 Gradient를 누적, 여러 Micro-Batch 뒤 Optimizer Step 실행.
- Checkpoint는 모델 가중치 외 Epoch, Optimizer, Scheduler 등 재개 상태를 포함할 수 있음. Kubernetes Job 재생성과 YOLO 학습 상태 복원은 별도 책임.
- 저장 주기는 체크포인트 오버헤드, 장애 위험, 복구 비용, 부서 요구조건, 저장소 요금에 따라 정함.
- GPU 이용률이 낮고 CPU 이용률이 높을 때 CPU 이미지 디코딩·증강·입력 파이프라인 병목 의심. 저장 I/O 및 단계별 처리 시간도 분리 측정.

## 서술형 인출 (답변과 피드백)
1. Batch Size 8→32에서 OOM 발생 이유?
   - 답: 한 번에 처리할 이미지가 많고 Gradient를 계산해야 하므로 메모리가 늘어남.
   - 피드백: 큰 원인은 배치 크기에 따른 Activation/입력 텐서 증가이며, 파라미터 Gradient 크기는 대체로 일정.
2. Batch 8×4 누적이 왜 32장 정보를 반영하는가?
   - 답: 8장씩 처리하는 만큼 순간 메모리 감소, 누적으로 32장 반영.
   - 피드백: 정확. 배치 감소는 절반이 아니라 1/4; Activation은 회차별 해제, Gradient만 누적.
3. Epoch 70에서 장애, S3 Epoch 50 체크포인트가 있으면 Pod 재생성만으로 재개되는가?
   - 답: 체크포인트에 가중치·설정 정보가 있으면 가능.
   - 피드백: 학습 재개 조건은 적절하나 Kubernetes가 자동으로 복원하지 않으며 YOLO resume 및 새 Pod의 S3·데이터셋 접근이 필요.
4. 3시간짜리 학습의 Checkpoint 저장 주기?
   - 답: 부서 요구사항과 저장 오버헤드를 고려해야 하므로 미리 확정하지 않는 것이 적절. 5분은 과할 수 있음.
   - 피드백: 합리적 운영 판단. 저장 비용, 유실 재학습 시간, 장애 확률 실제 측정 필요.
5. GPU 15%, VRAM 50%, CPU 95%, 학습 느림?
   - 답: GPU 업그레이드보다 CPU 이미지 디코딩·리사이징·증강 등 병목 우선. RunPod 사용 중 HDD 기반 느린 가중치 저장으로 학습이 지연됐던 경험 언급.
   - 피드백: 정확한 데이터 경로 기반 추정. CPU 바쁨과 저장 I/O 병목은 각각 측정하여 검증.
